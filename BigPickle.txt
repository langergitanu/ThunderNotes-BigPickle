BUILD-BREAKING (5):

B-1. app/src/main/res/layout/fragment_create_note.xml : 64, 109, 154, 208
     app:layout_margin="@dimen/space_xs"
     -> android:layout_margin="@dimen/space_xs"
     ERROR: AAPT "attribute layout_margin not found". layout_margin is a
     framework attribute — there is no app:layout_margin. The `app:` namespace
     is only for attributes the library defines. Also: GridLayout does not
     honour layout_margin the same way; these cards should use the GridLayout
     margin params if the intent was spacing between grid cells.

B-2. app/src/main/res/layout/fragment_thunder_home.xml : 54
     app/src/main/res/layout/fragment_notes_library.xml : 42
     style="@style/Widget.Material3.Button.IconButton.OutlinedButton"
     -> style="@style/Widget.Material3.Button.IconButton.Outlined"
     ERROR: "resource style/...IconButton.OutlinedButton not found".
     Self-check that it is a typo and not a real style: extracted material
     1.14.0 and listed every Widget.Material3.Button.IconButton.* style:
       IconButton, .Close.Snackbar, .Filled, .Filled.Tonal,
       .Filled.Tonal.ListItemRevealLayout, .ListItemRevealLayout,
       .Outlined, .Outlined.ListItemRevealLayout
     There is no ".OutlinedButton". ".Outlined" is the correct one.

B-3. app/src/main/java/com/thundernotes/ui/create/CreateNoteFragment.kt
     app/src/main/java/com/thundernotes/ui/create/ImportFileFragment.kt
     Both use R.string.* but neither imports com.thundernotes.R.
     ERROR: "Unresolved reference 'R'" at CreateNoteFragment.kt:65,88 and
     ImportFileFragment.kt:37. Added `import com.thundernotes.R` to each.
     NOTE: CoverSelectionFragment.kt also looked like it used bare R. but it
     only references android.R.color.darker_gray, so it is fine — do not
     "fix" that one.

B-4. app/src/main/java/com/thundernotes/MainActivity.kt : 45-48
     navController.navigate(destId) { launchSingleTop = true }
     ERROR: "Unresolved reference 'launchSingleTop'" + argument type mismatch.
     The `navigate { }` DSL + `launchSingleTop` need the navigation-common KTX
     `NavOptionsBuilder`, which is not what these artifacts expose at this
     version. Replaced with the stable API:
       navController.navigate(destId, null,
           NavOptions.Builder().setLaunchSingleTop(true).build())
     NOTE the null Bundle argument is REQUIRED: there is no
     navigate(int, NavOptions) overload. The overloads are
     navigate(int), navigate(int, Bundle), navigate(int, Bundle, NavOptions).
     I verified this by javap-ing NavController.class from
     navigation-runtime-2.7.7.aar.

CRASH ON LAUNCH (1) — this one boots then dies, so it is worse than a build error:

B-5. app/src/main/java/com/thundernotes/MainActivity.kt : 40
     navController = findNavController(R.id.nav_host)
     CRASH: "java.lang.IllegalStateException: Activity
     com.thundernotes.MainActivity@... does not have a NavController set on
     2131231076". MainActivity.onCreate, fresh install, every launch. The app
     showed the launcher screen for a moment then died. Replaced with:
       val navHostFragment = supportFragmentManager
           .findFragmentById(R.id.nav_host) as NavHostFragment
       navController = navHostFragment.navController
     WHY: the @id/nav_host is on the FragmentContainerView; Navigation's
     activity-level findNavController helper looks for the controller tag on a
     view / fragment at that id and does not find it on this view. Going
     through supportFragmentManager is the documented approach for
     FragmentContainerView-hosted NavHosts. (The old `<fragment
     android:name="NavHostFragment">` form is the one the activity helper was
     designed for.)

SECTION 2 — 3 REAL UI BUGS FOUND (user-reported, I root-caused all 3)
================================================================================
The most important thing to note: on 2 of these, the DATA IS CORRECT and the
BUG IS PURELY IN RENDERING. So a fix must touch the adapter/layout, not the
repo layer.

S2-1. FOLDER COLOR IS ALWAYS BLUE — and the stored color is ignored.
  User: "color can't be changed, I tried but the color picker didn't respond
         and they are all blue by default."
  EVIDENCE the picker DID work: the DB stored 3 different colors —
    Physics=3, Math=4, Computer Science=1 (indices into FOLDER_COLORS).
  So selection registered; rendering is what is broken. Two separate bugs:
    (a) app/src/main/res/layout/item_folder_card.xml : 30
        app:tint="@color/thunder_accent_blue"
        The folder icon tint is HARDCODED blue. It does not read folder.color.
    (b) app/src/main/java/com/thundernotes/ui/folders/FolderAdapter.kt : 47
        fun bind(folder) { binding.folderName.text = ...; bookmark visibility }
        `bind()` NEVER reads folder.color at all. So the card has no way to
        show the stored color even after (a) is fixed.
  FIX (yours): FolderAdapter.bind must map folder.color (an Int index) through
  the same FOLDER_COLORS palette used by CreateFolderFragment, and tint the
  icon (or a color dot) from it. Right now FOLDER_COLORS is a private val in
  CreateFolderFragment's companion — it needs to be shared (move it to a
  common place, e.g. ui/common/FolderColors.kt, so both the picker and the
  adapter use one source of truth; otherwise they will drift).
  SECONDARY: FolderAdapter is shared by Home, FoldersLibrary and Trash — all
  three screens will need the color once fixed. No screen currently shows it.

S2-2. COLOR PALETTE HAS DUPLICATE HUES.
  User: "two are red(different shades) and two are green(different shades) but
         they should be all distinct."
  app/src/main/java/com/thundernotes/ui/create/CreateFolderFragment.kt : 110-117
    FOLDER_COLORS = [ thunder_primary (crimson),
                      thunder_secondary (emerald),
                      thunder_tertiary (amber),
                      thunder_accent_blue (blue),
                      thunder_primary_dark (dark crimson),   <- dupe of #2
                      thunder_secondary_dark (dark emerald) ] <- dupe of #3
  Two reds + two greens by construction. Should be 6 visually distinct hues.
  There is no 6th distinct brand hue defined, so this needs either (a) new
  tokens, or (b) reusing a distinct-hue subset. Your call — flagging that the
  current palette cannot be "all distinct" without new colors.

S2-3. HOME SHOWS ONLY ONE RECENT FOLDER (layout, not data).
  User: "three folders should be displayed in home page's recent folder's area
         but only one appears."
  EVIDENCE the data is fine: all 3 folders are in the DB and all 3 render in
  the Folders page grid (user confirmed). Only the Home strip is wrong.
  ROOT CAUSE: app/src/main/res/layout/fragment_thunder_home.xml : 166
    recent_folders_recycler is LinearLayoutManager.HORIZONTAL, but the item it
    inflates — app/src/main/res/layout/item_folder_card.xml : 7 — is
    android:layout_width="match_parent".
    In a HORIZONTAL LinearLayoutManager, match_parent makes each card as wide
    as the entire strip, so the first card fills the viewport and the other two
    are laid out off-screen. (In the vertical grids this same match_parent is
    correct, which is why FoldersLibrary looks fine.)
  FIX (yours): give the Home strip either a fixed-width card variant, or a
  distinct item layout for the horizontal strip with a fixed width (e.g.
  180dp), and let the grid keep match_parent. Scoping it per-usage avoids
  breaking the 3-column grids that share item_folder_card.xml.

SECTION 3 — SMALLER OBSERVATIONS (no action required, but worth knowing)
================================================================================
  - W/WindowOnBackDispatcher on every modal: "OnBackInvokedCallback is not
    enabled ... Set android:enableOnBackInvokedCallback='true'". Harmless now,
    but Android 14+ predictive back is opt-in and this will matter once the
    canvas uses back navigation. Consider setting it in the manifest in Phase 6.
  - Note naming has no UI: createNote hardcodes "Untitled <MMM d HH:mm>" and
    the CreateNote sheet has no name field. Expected per spec; rename is in the
    (stubbed) overflow menu.
  - The recent-folders "match_parent in a horizontal list" class of bug is easy
    to reintroduce. If any OTHER horizontal RecyclerView is added later, check
    its item width.
